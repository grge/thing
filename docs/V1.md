# v1 is not a rewrite

Status: decided, 2026-09-02. Supersedes the framing — not the content — of
[ISSUES.md](ISSUES.md)'s **Rewrite** severity and its *For the rewrite* section.
The design v1 builds toward is [DESIGN.md](DESIGN.md); this is the route to it.
The issues stand; the conclusion that they need a fresh codebase does not.

The claim: **every change v1 needs is reachable by incremental edits to v0's
source, in a sequence where each step lands green on `master`.**

---

## Why the docs said "rewrite"

Two different things, which got conflated.

**"Rewrite" as a triage label.** [ISSUES.md](ISSUES.md)'s severity table defines
it as *"v0's design is insufficient for where this is going. Not a v0
obligation."* That is a statement about **scheduling** — it means "not now" — and
it is the sense carried by all nine issues tagged with it. It was never a
finding that the code would have to be discarded.

**"Rewrite" as an architectural claim.** One passage makes a real structural
argument, and it is narrower than it looks:

> The envelope (§2), the handshake (§3.4), and the blob/log boundary (§6) should
> be reconsidered **together**. They are the expensive things to change later,
> and I5, I6, I11, I13, I17 and I18 all land on one of the three.
> — [ISSUES.md](ISSUES.md#for-v1)

That argues for **coherence** — change those three in one coordinated move
rather than piecemeal — not for a greenfield start. And
[NEXT.md](NEXT.md#settled) has since removed most of its force by settling that
**mode 3 is out**, which drops the log/blob dichotomy, snapshots and compaction
"back to optional". The blob/log boundary was the expensive third of that
triple. It no longer has to move at all.

What remains is the envelope and the handshake, changing together, in one step.

## Why the code supports it

v0's layering already isolates the churn. The dependency graph runs one way:

- `src/net/` imports nothing from `app/` or `ui/`. The only crossing is
  `src/app/replication.ts:8-10`, which imports *into* `app` from `net`.
- `src/fold/` is a pure fold over an event log, with no knowledge of transport
  or storage. Everything else imports it; it imports nothing back.
- The addressing fusion that [NEXT.md](NEXT.md#open) calls "the hardest unsolved
  piece" is **five call sites**. `peerIdForCode` (`src/app/storage.ts:50`) is a
  one-line function, and outside its own module and tests it has exactly one
  caller: `src/ui/App.svelte:140`.

The three changes v1 actually needs are additive to structures that already
exist:

| Change | Where it lands | Shape |
|---|---|---|
| Signing (I5, I6, I7) | `Event` (`src/fold/types.ts:60`), `WireEvent` (`src/net/protocol.ts:28`) | two new fields, plus a verify step in `validate.ts` |
| Addressing split | `peerIdForCode` and its callers | a resolver behind the same seam |
| `:link` | the `AttrName` union (`src/fold/types.ts:26`) | one more member, one more `Value` variant |

`:link` is the tell. [NEXT.md](NEXT.md#open) argues it should be "an attribute
any object may carry" rather than a dedicated object type or a sidecar —
*because* that fits the existing model, where objects are bags of attributes and
`:kind` is explicitly advisory (§4.6). The design reasoning already converged on
something the current type union absorbs by adding a line to it.

## Zero migration

**There is no backwards compatibility obligation to v0, in any form.** Nothing
in v1 needs to read, convert, upgrade, or interoperate with anything v0 wrote.

This is not a cost being deferred. It is a cost that **does not exist**, and it
is what makes the incremental path cheap rather than merely possible. Concretely,
none of the following is v1 work:

- **No data migration.** v0 logs in localStorage stay where they are and are
  simply not read by v1. No converter, no upgrade-on-open path, no dual-format
  reader in the fold.
- **No wire compatibility.** A v1 peer does not have to talk to a v0 peer.
  `PROTOCOL_VERSION` (`src/net/protocol.ts:11`) gets bumped and the handshake
  rejects the mismatch — which is all the version field was ever for.
- **No envelope compatibility.** Signing changes the hash preimage, so
  `src/fold/encode.ts` changes and every v0 event becomes unverifiable under v1.
  That is fine and expected. It is the *reason* signing is step 1 rather than a
  later retrofit.
- **No share-code compatibility.** v0 share links may break. The 8-character
  code is demoted from identity to bootstrap hint
  ([NEXT.md](NEXT.md#open)); old links pointing at the old scheme are not owed
  resolution.
- **No stored-state compatibility.** Settings, peer state and blob stores may be
  dropped or reshaped freely.

The licence for this is already on the record: v0 is *"a throwaway proof of
concept"* ([README](../README.md)), its spec is *"scoped to a throwaway proof of
concept"* ([SPEC.md](v0/SPEC.md)), and [NEXT.md](NEXT.md) states the next iteration
is likewise *"a throwaway experiment"*. There is no user data, no deployment
anyone depends on, and no second implementation to keep in step.

**The practical consequence:** when a v1 change would be easier if it could
ignore existing data, it should ignore existing data. Wipe and recreate is the
default answer. If a step ever seems to call for a compatibility shim, that is a
signal the step is wrong, not that a shim is needed.

**What "incremental" does and does not mean here.** It means editing v0's source
in place, keeping the layering, the tests and the working parts, rather than
starting an empty directory. It does *not* mean preserving v0's behaviour,
formats or data. The codebase is continuous; the artefacts it produces are not.

## The sequence

Three steps on `master`, each landing green.

### 1. Signing — **done**

First, because it is the change that touches the envelope, and because I5, I6
and I7 all resolve from it. Doing it first also means step 2 builds on real keys
rather than a placeholder that would have to be replaced.

This is where [ISSUES.md](ISSUES.md#for-v1)'s "reconsider together"
warning is honoured: the envelope and the handshake change in one coordinated
move. The blob/log boundary — the third member of that triple — does not move,
because mode 3 is out.

Specified in [DESIGN.md](DESIGN.md) §5. Resolves
[I5](ISSUES.md#i5-lamport-clocks-are-unenforceable-so-a-malicious-peer-wins-every-conflict--fixed-in-v1)
and [I6](ISSUES.md#i6-hello-is-unauthenticated-any-peer-can-claim-any-writer-id--fixed-in-v1);
[I7](ISSUES.md#i7-share-codes-cannot-be-revoked-or-rotated--rewrite) needs step 2
as well, since the code is still an identity until addressing splits.

**Built.** `WriterId` widened to a 32-byte public key, `sig` added to the
envelope and verified at the wire boundary, keys persisted as extractable seeds,
`PROTOCOL_VERSION` bumped to 2. The prediction that this was reachable
incrementally held: TypeScript found the entire blast radius as **three**
missing-field errors, and no layer boundary moved.

### 2. Addressing

Specified in [DESIGN.md](DESIGN.md) §4. Space id = public key, which falls out
of step 1 nearly for free. Adds a petname
layer in the UI and demotes the short code to a bootstrap hint, per
[ADDRESSING.md](ADDRESSING.md) and [NEXT.md](NEXT.md#open).

The seam is already there: `peerIdForCode` becomes a resolver, and its one real
caller (`src/ui/App.svelte:140`) is the only place that has to learn the
difference between identity and location.

### 3. `:link`

Specified in [DESIGN.md](DESIGN.md) §2.1. Last, because a link needs a stable
target to point at, which is exactly what
step 2 produces. Purely additive once identity is a key.

## The invasive part, stated plainly

One change is genuinely broad, and it should be decided **before step 1 starts**:

> **Does `WriterId` become a full 32-byte public key, or a hash of one?**

`WriterId` (`src/fold/types.ts:6`) is currently 16 bytes (`WRITER_LEN`).
Widening it propagates through version vectors (`VersionVector` keys,
`src/net/protocol.ts:26`), the `prev` chain, and the `(lamport, writer)`
comparison used throughout the fold. The work is mechanical — writer identity
already routes through one named type — but it is broad, and it is annoying to
reverse once tests and fixtures are written against a width.

Note that truncation is not free either: [NEXT.md](NEXT.md#open) records that
shortening by truncating a hash is grindable, and
[I14](ISSUES.md#i14-truncated-16-byte-hashes-are-not-adversary-resistant--rewrite)
already flags 16-byte hashes as not adversary-resistant. Whatever is chosen, it
should be chosen for a stated reason rather than inherited from v0's 16.

---

## What this does not claim

- **Not that v1 is small.** Signing, addressing and links are real work.
  Incremental means *the codebase survives*, not *the change is cheap*.
- **Not that the issues were wrong.** Every **Rewrite**-tagged issue in
  [ISSUES.md](ISSUES.md) still describes a real insufficiency. This document
  disputes only the implied remedy.
- **Not that v1 is the destination.** [NEXT.md](NEXT.md) is explicit that the
  next iteration is itself a throwaway experiment. Continuity of the codebase is
  a convenience, not a commitment to it.
